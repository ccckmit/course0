📖 課程概述

本課程介紹 AI 導向的現代軟體開發方法論，重點在於如何與 AI 協作、建立完善的測試體系、設計清晰的 API、以及運用 Git 和 CI/CD 管線。課程內容對應 The Modern Software 線上教材，以及本倉庫的 code/軟體工程/ 範例和 wiki/軟體工程/ 知識庫。

三大支柱

  • AI 協作 — Prompt、Context、Harness、Skill 四大工程
  • 測試先行 — 測試金字塔、pytest、Playwright、test.sh
  • API 驅動 — CLI → REST → React 的前後端分離

開發紀律

  • Git 工作流 — 分支策略、Pull Request、Code Review
  • CI/CD — 自動化建構、測試、部署
  • KISS 原則 — Keep It Simple, Stupid

⚡ 語言與工具對效能的影響

同一份 Todo 應用分別用 Python (FastAPI) 和 Rust (Axum + SQLite / sled + Redis) 實作，展示語言與架構選擇對執行效能和開發體驗的差異。

核心指標對比

▶
# Python Rust+SQLite Rust+sled+Redis+Nginx # 啟動時間 ~500ms ~8ms ~10ms # 記憶體 (idle) ~80MB ~5MB ~12MB # 吞吐量 ~12k req/s ~128k req/s ~450k req/s # 延遲 p99 ~15ms ~1.2ms ~0.2ms # 開發速度 Python 快 Rust 慢 (編譯) Rust 慢 (編譯) # 型別安全 執行期檢查 編譯期保證 編譯期保證 # 部署 需 runtime 靜態二進位 靜態二進位

為什麼 Rust 更快

▶
# 1. 啟動時間 # Python: 載入直譯器 + 匯入模組 + ASGI 初始化 # Rust: 作業系統直接載入原生二進位 # 2. 記憶體 # Python 物件開銷大: int=28B, str=49B+字元, GC 追蹤 # Rust 值類型: i64=8B, String=24B(stack)+heap, 無 GC # 3. 吞吐量 # FastAPI (ASGI): 單執行緒事件循環, SQLite I/O 阻塞 # Axum (tokio): 多執行緒 async, SQLite 透過 spawn_blocking # sled (mmap): 鎖自由資料結構 + memory-mapped I/O # Redis 快取: 減少 sled 查詢, read-heavy 場景 ~1.7x 增益 # Nginx proxy: keepalive + proxy_cache, 大量請求 ~1.3x 增益

選擇建議

▶
# 選 Python (FastAPI) 當： # • 快速原型開發 # • 團隊 Python 經驗豐富 # • 開發速度比執行效能重要 # • 部署在 Serverless 平台 # 選 Rust (Axum + SQLite) 當： # • 高效能需求 (高吞吐、低延遲) # • 記憶體受限環境 (容器、邊緣運算) # • 需要編譯期安全保證 # • 部署為靜態二進位 (無 runtime 依賴) # 選 Rust + sled + Redis + Nginx 當： # • 極致效能需求 (~37x Python) # • read-heavy 工作負載 (Redis 快取) # • 需要選用快取 + 反向代理架構

🤖 AI 協作開發

Prompt 工程

▶

Prompt 工程是與 AI 溝通的核心技能。好的 Prompt 包含明確的角色定義、任務描述、輸出格式和約束條件。

# Prompt 最佳實踐 # 1. 角色定義：你是一位 Rust 系統程式專家 # 2. 任務描述：實作一個記憶體池分配器 # 3. 輸出格式：提供完整程式碼和測試 # 4. 約束條件：unsafe 程式碼需附 Safety 註解 # Few-shot 範例：提供輸入/輸出對 # CoT (Chain of Thought)：要求逐步思考
wiki/Prompt工程.md Prompting Guide

Context 工程

▶

Context 工程是 Prompt 工程的延伸，專注於設計和管理與 AI 智慧體互動時的上下文策略。根據 Prompting Guide，這是構建可靠 AI 智慧體的關鍵實踐。

# Context 的四層結構 # System Context ─ 角色定義、能力邊界、行為約束 # Task Context ─ 任務描述、成功標準、預期輸出 # Tool Context ─ 工具描述、使用時機、錯誤處理 # Memory Context ─ 對話歷史、任務狀態、學習記錄 # 核心問題與解決方案 # Issue 1: 不完整執行 → 明確要求完成所有任務 # Issue 2: 工具誤用 → 分階段授予工具權限 # Issue 3: 上下文遺忘 → 使用 todo.md 記錄狀態 # Issue 4: 幻覺 → 強制引用來源
wiki/Context工程.md

Harness 工程

▶

Harness Engineering（馭繮工程）是 OpenAI 在 2026 年提出的範式：工程師不再寫代碼，而是設計環境、明確意圖、建構反饋迴圈。人類變成「掌舵者」，AI 是「執行者」。

# 傳統工程 vs Harness Engineering # 傳統：人類寫代碼 → 機器執行代碼 # Harness：人類設計約束 → AI 寫代碼 → 機器執行 # 六大核心概念 # 1. 倉庫即記錄系統 — 不在倉庫裡的東西對 AI 不存在 # 2. AGENTS.md — 目錄而非百科，~100行，只指路 # 3. 專職 linter — 知識庫是否更新、交叉連結是否完整 # 4. 執行計畫為一等工件 — 提交到倉庫，版本控制 # 5. 人類驗證 — AI 發 PR，人類 Review 合併 # 6. 反饋迴圈 — lint → test → review → revise
wiki/Harness工程.md OpenAI 原文 Harness 學習指南

Skill 文檔

▶

Skill 是 AI 擴展機制，將領域知識封裝成可重用的套件。AI 根據任務自動發現並載入相關 Skill。

# Skill vs 其他機制 # MCP Servers → 工具調用（需知道存在） # Slash Commands → 預定義 Prompt（手動呼叫） # Skills → 領域知識（自動發現） # AGENTS.md → 基本規則（始終載入） # Skill = 專業知識 + 執行指引 + 輔助工具 # 資料夾結構 # .claude/skills/ # ├── pdf/ # │ ├── SKILL.md # 必需：Skill 定義 # │ ├── extract_text.ts # 可選：輔助腳本 # │ └── templates/ # 可選：資源 # └── ...
wiki/Skill文檔.md docs/skill/ 定義

Loop 工程

▶

Loop Engineering（反饋迴圈工程）是設計和管理 AI 輔助開發中多層反饋迴圈的實踐。從程式碼生成的即時檢查到跨 Sprint 的迭代改進，每一層迴圈決定開發效率和品質。

# 三層迴圈模型 # 外層：人類 Prompt → AI 生成 → 人類驗證 → 迭代 # 中層：程式碼 → 測試 → Lint → 自動修復 → 重新測試 # 內層：AI 生成 → 語法檢查 → 自行修正 → 重新生成 # 設計原則 # • 快速失敗：內層毫秒級、中層秒級、外層分鐘級 # • 自動化閘門：每一層出口設置檢查 # • 可見性：迴圈狀態可追蹤
wiki/Loop工程.md

Agentic 工程

▶

Agentic Engineering（智慧體工程）是設計和建構自主 AI 智慧體的實踐。智慧體能感知環境、規劃行動、使用工具、執行任務，並在過程中自主決策。是 Prompt → Context → Harness → Loop 之後的進階範式。

# Agent 核心循環 # 感知 (Perceive) → 規劃 (Plan) → 執行 (Act) → 觀察 (Observe) # Agent 架構組件 # • 模型 — 推理與決策核心 # • 規劃器 — 分解任務、制定步驟 (ReAct, Plan-and-Execute) # • 工具 — 與外部互動 (程式碼執行器、API) # • 記憶 — 上下文和經驗 (對話記錄、向量資料庫) # • 安全層 — 約束和驗證 (權限控制、輸出過濾) # 範式演進 # Prompt → Context → Harness → Loop → Agentic
wiki/Agentic工程.md wiki/Agent發展史.md

🧪 測試策略

測試金字塔

測試金字塔是測試策略的核心指導原則：

E2E 測試 (Playwright) — 慢、貴、少
整合測試 (API/DB) — 中等
單元測試 (pytest) — 快、便宜、多

pytest 單元測試

▶

Python 專案使用 pytest 作為測試框架，測試檔案命名為 test_*.py：

# test_calculator.py import pytest from calculator import add, divide def test_add(): assert add(2, 3) == 5 assert add(-1, 1) == 0 def test_divide_by_zero(): with pytest.raises(ValueError): divide(1, 0) # 執行: python -m pytest 或 pytest
wiki/測試.md todo/test_cli.py todo/test_api.py

Playwright E2E 測試

▶

網站專案使用 Playwright 進行端到端測試，模擬真實用戶操作：

# test_e2e.py — Playwright E2E 範例 from playwright.sync_api import sync_playwright def test_blog_homepage(): with sync_playwright() as p: browser = p.chromium.launch() page = browser.new_page() page.goto("http://localhost:3000") assert page.title() == "部落格" assert page.text_content("h1") == "最新文章" browser.close()

test.sh 腳本

▶

每個專案必須有 test.sh 作為統一測試入口，使用 set -x 顯示執行的命令：

#!/bin/bash set -x # 顯示每條命令 pytest -v # Python 測試 ruff check . # Lint 檢查 python -c "import main; print('OK')" # 基本匯入測試

▶

▶

# 金流整合常見模式 # 1. 第三方支付閘道 (Third-Party Payment Gateway) # • 藍新、綠界、LINE Pay、街口 # • 特店設定 → API 串接 → 測試 → 正式上線 # • 手續費: 2%~3% + 每筆固定費用 # # 2. 信用卡收款 (Credit Card) # • Stripe、TapPay、直接與收單行串接 # • PCI-DSS 合規要求 (每年安檢) # • 3D 驗證 (3D Secure) 降低爭議款 # # 3. 超商代收 / ATM 轉帳 # • 適合非即時付款場景 (繳費單) # • 對帳批次: T+1 工作日 # # 4. 訂閱制 / 定期定額 (Subscription) # • 週期性扣款 (月/季/年) # • 需處理續約失敗、信用卡換發 # # 技術實作要點 # • 交易記錄不可竄改 (資料庫 append-only) # • 金流 Log 需完整保留 (稽核需求) # • 失敗重試 + 補償交易 (Saga 模式) # • 定期對帳 (Reconciliation): 比對訂單 vs 銀行入帳

公司登記與開業

▶
# 軟體公司設立流程 (台灣) # 1. 公司名稱預查 — 經濟部商業司 # 2. 公司設立登記 — 股份有限公司 / 有限公司 # • 資本額: 無最低限制 (但需會計師簽證) # • 董事、監察人、股東名冊 # # 3. 營業項目登記 # • I301010 資訊軟體服務業 # • I301020 資料處理服務業 # • I301030 電子資訊供應服務業 # • F118010 資訊軟體批發業 # # 4. 稅籍登記 + 統一發票 # • 營業稅: 5% (可扣抵進項) # • 營所稅: 20% # # 5. 特店申請 (如需收款) # • 銀行或第三方支付閘道 # • 需提供公司登記證明 + 營業計畫 # # 6. 網站 / 產品上線前檢查 # • 隱私權條款 + 服務條款 # • 金流合約審閱 # • 消費者保護法: 7 天鑑賞期 # • 個人資料保護法 (個資法) 合規

上線營運

▶
# 上線前檢查清單 (Go-Live Checklist) # □ 功能測試完成 (含邊界案例) # □ 壓力測試 / 效能驗證 # □ 備份機制 (資料庫自動備份) # □ 監控建置 (Server / 資料庫 / 金流) # □ 錯誤通知 (Email / Slack / LINE 通知) # □ 日誌集中管理 (ELK / Loki + Grafana) # □ DNS 設定 + SSL 憑證 # □ 業務連續性計畫 (BCP / 災難復原) # # 上線後營運 # • 每日: 檢查金流對帳、Error Log、備份狀態 # • 每週: 部署更新、安全性修補 # • 每月: 財務報表、金流手續費分析 # • 每季: 法規更新檢視 (個資法、消費者保護) # # 常見上線問題 # • SSL 憑證過期 — 設定自動續約 (Let's Encrypt) # • 資料庫連線耗盡 — Connection Pool 設定 # • 第三方 API 失效 — 熔斷機制 (Circuit Breaker) # • 金流交易失敗 — 補償機制 + 通知客服 # • 大量請求 — Auto Scaling + Rate Limiting
