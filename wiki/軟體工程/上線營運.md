# 上線營運

軟體產品從開發完成到正式上線是一個關鍵轉折點，需要從技術、業務、營運多個面向做準備。本章涵蓋上線前檢查、上線後營運、常見問題處理。

## 上線前檢查清單 (Go-Live Checklist)

### 功能與測試

- [ ] 所有 User Story 驗收完成
- [ ] 邊界案例測試（空值、最大長度、並發）
- [ ] 跨瀏覽器 / 跨裝置測試
- [ ] API 整合測試全數通過
- [ ] E2E 測試（關鍵流程覆蓋）
- [ ] 壓力測試（預期流量 2x~5x）

### 基礎設施

- [ ] 資料庫自動備份設定（每日 + 交易日誌）
- [ ] CDN 設定（靜態資源加速）
- [ ] DNS 設定 + CNAME / A Record
- [ ] SSL 憑證（Let's Encrypt 自動續約）
- [ ] 負載平衡器 / Auto Scaling 設定

### 監控與通知

- [ ] Server 監控 (CPU / Memory / Disk)
- [ ] 資料庫監控 (Connection / Query / Slow Log)
- [ ] 金流交易監控（成功率、異常率）
- [ ] 錯誤通知（Email / Slack / LINE）
- [ ] 日誌集中管理（ELK / Loki + Grafana）

### 備援與復原

- [ ] 多可用區部署 (Multi-AZ)
- [ ] 資料庫跨區域備份
- [ ] 災難復原演練 (RTO < 4h, RPO < 1h)
- [ ] Status Page 設定（服務中斷通知頁面）

### 法規與合約

- [ ] 服務條款 (ToS) 上線
- [ ] 隱私權條款上線
- [ ] 金流合約審閱完成
- [ ] 退費政策公告
- [ ] 消費者保護法規遵循

## 上線策略

| 策略 | 說明 | 優點 | 風險 |
|------|------|------|------|
| Big Bang | 一次性全面上線 | 簡單、開發成本低 | 風險最高，問題影響所有用戶 |
| Phased Rollout | 分批上線（區域/用戶群） | 逐步驗證，可控風險 | 需要功能開關（Feature Flag） |
| Blue-Green | 兩套環境切換 | 快速回滾 | 需要雙倍資源 |
| Canary | 先導少量用戶 | 即時回饋，最小影響 | 需監控 + 自動 Rollback |

**建議**：新創團隊可先做 Phased Rollout + Feature Flag，成熟後導入 Blue-Green。

## 上線後營運週期

### 每日

```
1. 檢查金流對帳 — 昨日的訂單 vs 銀行入帳
2. 檢查 Error Log — 是否有新的異常
3. 檢查備份狀態 — 資料庫備份成功
4. 檢查 Server 指標 — CPU / Memory / Disk
```

### 每週

```
1. 部署更新 — Bug 修復、小功能
2. 安全性修補 — Dependencies / OS 更新
3. 資料庫維護 — 索引最佳化、清理舊資料
4. Review 監控告警 — 調整閾值
```

### 每月

```
1. 財務報表 — 營收、成本、金流手續費
2. 金流分析 — 付款方式分布、失敗原因
3. 效能回顧 — API 延遲趨勢、資料庫查詢
4. 用戶留存分析 — Cohort、Churn Rate
```

### 每季

```
1. 法規更新檢視 — 個資法、消保法、稅務
2. 安全稽核 — PCI-DSS / 第三方安檢
3. 災難復原演練 — 模擬故障情境
4. 技術債盤點 — 重構計畫
```

## 常見上線問題

### SSL 憑證過期

- 症狀：瀏覽器顯示「不安全」
- 預防：Let's Encrypt 自動續約（Certbot / acme.sh）
- 監控：到期前 30 天、14 天、7 天、1 天發送通知

### 資料庫連線耗盡

- 症狀：API 回應 500 / 連線超時
- 原因：Connection Pool 太小、慢查詢堆積連線、無連線釋放
- 解決：
  - 設定 Pool 上限（例：MySQL `max_connections=200`）
  - 設定連線超時（`wait_timeout=60`）
  - 使用 PgBouncer / ProxySQL 管理連線池

### 第三方 API 失效

- 症狀：金流付款失敗、簡訊發送失敗
- 預防：
  - 熔斷機制（Circuit Breaker）— 連續失敗後自動切斷
  - 降級策略 — 顯示「暫時無法使用」而非 500
  - 備援廠商 — 主要 + 備援閘道

### 大量請求 (Traffic Spike)

- 症狀：回應變慢、502 / 503
- 預防：
  - Auto Scaling — 根據 CPU / 請求數自動擴展
  - Rate Limiting — 限制單 IP / 單用戶請求次數
  - CDN 快取 — 靜態資源 / API 回應快取
  - 資料庫 Read Replica — 讀取分擔
