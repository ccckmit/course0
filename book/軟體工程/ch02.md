# 大型語言模型基礎

## 概述

大型語言模型（Large Language Model, LLM）是 AI 軟體工程的核心技術基礎。無論是程式碼生成、程式碼補全、程式碼審查還是測試案例生成，其底層都是各種 LLM 在發揮作用。要有效地運用這些模型，就需要對它們的運作原理有基本的理解。

本章將從三個層面介紹 LLM 的核心技術。第一是模型架構，我們將深入解析 Transformer 的設計原理，包括自注意力機制、多頭注意力、位置編碼等關鍵技術。第二是訓練方法，我們將介紹從預訓練到指令微調再到 RLHF 的完整訓練流程。第三是推理機制，我們將討論自回歸生成、解碼策略與上下文視窗等概念。

此外，本章還將介紹專門針對程式碼進行最佳化的模型（如 Codex、StarCoder、Code Llama、DeepSeek Coder）以及 embeddings 與向量表示的基本概念。

## Transformer 架構

Transformer 架構由 Vaswani 等人在 2017 年發表，是現代 LLM 的基石。在此之前，自然語言處理領域的主流模型是遞迴神經網路（RNN）與長短期記憶網路（LSTM）。RNN 按順序處理序列中的每個元素，這使得它們難以平行化，訓練速度較慢。此外，RNN 在處理長序列時存在梯度消失與梯度爆炸的問題，即使 LSTM 對此有所改善，但本質上的序列處理限制仍然存在。

Transformer 的核心創新在於完全摒棄了遞迴結構，轉而使用注意力機制（Attention Mechanism）來捕捉序列中各個位置之間的關聯。這使得 Transformer 可以平行處理整個序列，大幅提升了訓練效率，同時也能夠更好地捕捉長距離依賴關係。

### Transformer 的整體結構

Transformer 採用編碼器-解碼器（encoder-decoder）的架構設計。編碼器負責將輸入序列轉換為一組連續的表示（representations），解碼器則根據編碼器的輸出以及已經生成的輸出序列來逐步生成目標序列。

在原本的 Transformer 論文中，編碼器與解碼器各由 6 層（layer）組成。每一層編碼器包含兩個子層：一個是自注意力層（self-attention layer），另一個是前饋神經網路層（feed-forward neural network layer）。每一層解碼器則包含三個子層：一個是遮罩自注意力層（masked self-attention layer）、一個是編碼器-解碼器注意力層（encoder-decoder attention layer）、以及一個前饋神經網路層。每個子層周圍都有殘差連接（residual connection）與層歸一化（layer normalization）。

殘差連接讓梯度可以直接流經整個網路，有助於訓練深層模型，解決了深層網路常見的退化問題。層歸一化則透過將每一層的輸出標準化來穩定訓練過程，使其收斂更快且更穩定。

### 注意力機制

注意力機制的核心思想是：在處理序列中的某個元素時，模型可以關注（attend to）序列中所有其他元素，並根據它們與當前元素的相關性來加權整合資訊。

具體而言，注意力函式將一個查詢（query）與一組鍵值對（key-value pairs）映射到一個輸出。輸出是值的加權總和，其中每個值的權重由查詢與對應的鍵計算得到。

```
Attention(Q, K, V) = softmax(QK^T / sqrt(d_k)) V
```

其中 Q 是查詢矩陣，K 是鍵矩陣，V 是值矩陣，d_k 是鍵向量的維度。除以 sqrt(d_k) 是為了防止內積的值過大，避免 softmax 函式的梯度進入飽和區域。

注意力機制的優雅之處在於，它可以捕捉序列中任意兩個位置之間的關係，無論它們相隔多遠。在自然語言處理中，這意味著模型可以在生成當前單詞時考慮到句子開頭的主語，即使主語與當前單詞之間隔了很長的修飾語。在程式碼生成中，這意味著模型可以在生成一個函式呼叫時考慮到該函式在程式碼中較早位置的定義。

### 多頭注意力

Transformer 使用多頭注意力（Multi-Head Attention）來進一步提升注意力機制的表達能力。多頭注意力的概念是，與其使用一個注意力函式，不如使用多個不同的注意力頭（attention head）平行地計算注意力，然後將結果拼接（concatenate）起來。

```
MultiHead(Q, K, V) = Concat(head_1, ..., head_h) W^O
其中 head_i = Attention(QW_i^Q, KW_i^K, VW_i^V)
```

每個注意力頭使用不同的線性投影矩陣（W_i^Q、W_i^K、W_i^V），因此可以從不同的角度關注序列中的不同部分。例如，在程式碼生成任務中，一個頭可能關注變數的型別資訊，另一個頭可能關注變數的使用方式，還有一個頭可能關注相關的函式簽章。這些不同的關注角度共同構成了模型對輸入的豐富理解。

實驗表明，多頭注意力顯著優於單頭注意力，且增加頭數在一定的範圍內可以持續提升效能。在 GPT-3 中，每個注意力層使用了 96 個頭。

### 位置編碼

由於 Transformer 沒有遞迴結構，它無法像 RNN 那樣自然地感知序列中元素的順序。如果沒有位置資訊，模型會將輸入序列視為一組無序的集合。為了解決這個問題，Transformer 需要顯式地為每個位置添加位置編碼（Positional Encoding）。

在原始的 Transformer 論文中，位置編碼使用正弦與餘弦函式來生成：

```
PE(pos, 2i) = sin(pos / 10000^(2i/d_model))
PE(pos, 2i+1) = cos(pos / 10000^(2i/d_model))
```

其中 pos 是位置索引，i 是維度索引，d_model 是模型的隱藏層維度。

這種設計有幾個優點。首先，正弦與餘弦函式在 -1 到 1 之間取值，與模型的其他部分數值範圍一致。其次，不同頻率的正弦與餘弦函式允許模型輕易地學習到相對位置關係——因為對於固定的偏移量 k，PE(pos+k) 可以表示為 PE(pos) 的線性函式。最後，這種編碼方式沒有可學習的參數，可以直接計算，且可以推廣到訓練時未見過的序列長度。

後續的研究提出了許多改進的位置編碼方案。學習式位置編碼（learned positional embedding）讓模型在訓練過程中自行學習位置表示，如 GPT 系列模型中所使用的。旋轉位置編碼（Rotary Position Embedding, RoPE）將位置資訊編碼到查詢與鍵向量的內積計算中，在 Llama、Mistral 等現代模型中廣泛使用。ALiBi（Attention with Linear Biases）則在注意力分數中加入與位置距離成正比的偏置項，讓模型可以隱式地感知位置關係。

### 編碼器-解碼器 vs 僅解碼器架構

雖然原始的 Transformer 採用編碼器-解碼器架構，但後續的研究發現，對於不同的任務類型，可以採用不同的架構簡化方案。

BERT 採用僅編碼器（encoder-only）架構，適合需要理解完整輸入的任務，如文字分類、命名實體識別等。GPT 系列採用僅解碼器（decoder-only）架構，適合生成式任務。僅解碼器架構的優點是架構簡單，可以透過自回歸的方式從左到右逐步生成序列，非常適合語言生成任務。目前主流的程式碼生成模型（GPT-4、Claude、Code Llama、DeepSeek Coder 等）都採用僅解碼器架構。

T5（Text-to-Text Transfer Transformer）則重新使用了編碼器-解碼器架構，並統一了各種 NLP 任務的格式——將所有任務都視為文字到文字的轉換。程式碼專用模型 CodeT5 繼承了這一設計。

## 訓練流程

LLM 的訓練通常分為三個主要階段：預訓練（pre-training）、指令微調（instruction fine-tuning）與強化學習從人類回饋（Reinforcement Learning from Human Feedback, RLHF）。這三個階段各有不同的目標與方法。

### 預訓練

預訓練是 LLM 訓練的第一個階段，也是計算成本最高的階段。預訓練的目標是在大規模的無標註文字資料上學習語言的統計規律，包括詞彙、語法、語意、常識知識等。

預訓練的任務通常是語言建模（language modeling）。對於僅解碼器模型，語言建模的目標是根據前面的 token 序列來預測下一個 token。這個任務稱為「自回歸語言建模」，其損失函式是交叉熵損失（cross-entropy loss）。

```
L = - sum log P(token_t | token_1, ..., token_{t-1})
```

預訓練資料的規模極為龐大。GPT-3 使用了約 570GB 的文字資料，Llama 3 使用了約 15 兆個 token。資料來源包括網頁爬取（Common Crawl）、書籍、論文、維基百科、程式碼（GitHub）等。資料的品質對模型效能有顯著影響，因此預訓練資料的清洗與過濾是一個重要的工程環節。

預訓練通常需要數千到數萬個 GPU 天。例如，訓練 GPT-3 估計使用了數千個 GPU 連續訓練了數週。由於預訓練成本極高，很少有團隊從頭開始預訓練一個 LLM——大多數開發者與研究人員的工作基於已經預訓練好的基礎模型進行微調。

### Fill in the Middle (FIM)

對於程式碼專用模型，預訓練任務除了標準的從左到右語言建模之外，還有一個重要的變體：Fill in the Middle（FIM）。FIM 的目標是根據前文與後文來預測中間的程式碼片段。

```
def fibonacci(n):
    if n <= 0:
        return []
    <FILL_HERE>
    for i in range(2, n):
        fib.append(fib[i-1] + fib[i-2])
    return fib
```

在這種任務中，模型需要根據前文（def fibonacci 到 return []）與後文（for i in range 到 return fib）來推斷中間應該填入的程式碼。這種訓練方式讓模型具備了強大的程式碼補全能力——在 IDE 中，當開發者在檔案中間位置開始輸入時，模型可以同時使用游標之前的內容與之後的內容來預測應該填入的程式碼。

FIM 任務由 OpenAI 在 Codex 中首次大規模應用，後來被 StarCoder、Code Llama、DeepSeek Coder 等模型廣泛採用。

### 指令微調

經過預訓練的模型雖然具備豐富的語言知識，但並不擅長遵循人類的指令。例如，如果我們直接問一個預訓練模型「請用 Python 寫一個快速排序的實作」，它可能無法正確理解這個請求。指令微調就是為了解決這個問題而設計的。

指令微調的過程如下。首先，收集大量的人類編寫的指令-回應對（instruction-response pairs），例如：

```
指令：用 Python 寫一個快速排序函式
回應：def quick_sort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[len(arr) // 2]
    ...
```

然後，在這些資料上對預訓練模型進行微調，讓模型學會根據指令給出適當的回應。微調的目標函式與預訓練類似——最大化正確回應的機率——但只在指令資料上進行訓練。

指令微調的關鍵在於資料的品質與多樣性。高品質的指令資料應該涵蓋各種任務類型（生成、分類、摘要、翻譯、程式碼撰寫等）、各種難度等級、以及各種風格偏好。資料的數量通常在數萬到數百萬條之間，遠少於預訓練資料，但品質遠高於預訓練資料。

指令微調極大地提升了模型的可用性。經過指令微調的模型（如 GPT-3.5、Claude 3）能夠理解並遵循複雜的指令，在各種任務上表現出色，並且具有更好的對話能力。

### 監督式微調

除了通用的指令微調之外，針對特定領域或特定任務的監督式微調（Supervised Fine-Tuning, SFT）也是一種常見的做法。例如，將一個通用的 LLM 在大量的程式碼相關資料上進行微調，可以得到專注於程式碼生成的模型。

Codex 就是一個典型的例子。OpenAI 在 GPT-3 的基礎上，使用了從 GitHub 收集的大量高品質程式碼資料進行微調，得到了專注於程式碼生成任務的 Codex 模型。微調資料既包含純程式碼（用於提升語言建模能力），也包含自然語言-程式碼配對資料（用於提升從描述生成程式碼的能力）。

SFT 的優點是：需要的計算資源遠少於預訓練（可以在單個或多個 GPU 上完成）；可以針對特定任務進行最佳化；可以快速迭代，適應新的需求或領域。

### 強化學習從人類回饋

RLHF 是 LLM 訓練的第三個階段，由 OpenAI 在 InstructGPT 論文中提出，後來被廣泛應用。RLHF 的目標是讓模型的輸出更加符合人類的偏好——更安全、更有幫助、更誠實。

RLHF 的流程分為三個步驟。

第一步是收集人類偏好資料。給定一個 prompt，讓模型生成多個不同的回應，然後由人類標註者對這些回應進行排序（從最好到最差）。這個過程會產生大量的「偏好對」（preference pairs），用來訓練獎勵模型（reward model）。

第二步是訓練獎勵模型。獎勵模型是一個二分類模型，其任務是給定一個回應，預測人類會給予它的評分。獎勵模型的訓練資料來自上一步收集的人類偏好資料，訓練目標是盡可能準確地預測人類的偏好排序。

第三步是使用強化學習來微調 LLM。具體做法是使用近端策略最佳化（Proximal Policy Optimization, PPO）演算法，以獎勵模型給出的評分為獎勵訊號，來微調 LLM 的參數。在微調過程中，LLM 被鼓勵生成獎勵模型評分高的回應，同時避免偏離原始模型太遠（透過 KL 散度正則項來約束）。

RLHF 在提升模型的安全性與有用性方面效果顯著。然而，這個過程也存在一些問題：對人類標註者的依賴使得成本高昂；人類偏好的收集可能引入標註者的偏見；獎勵模型可能被「駭」——模型學會生成表面看起來很好但實際上品質不高的回應。

RLHF 的替代方案也在持續發展之中。直接偏好最佳化（Direct Preference Optimization, DPO）簡化了 RLHF 流程，不需要單獨訓練獎勵模型，而是直接在偏好資料上對 LLM 進行微調。DPO 的方法更簡單、訓練更穩定，在多個基準測試上取得了與 RLHF 相當的效果。

### 參數高效微調

對於大多數開發者與團隊來說，從頭開始預訓練一個 LLM 是不現實的——預訓練需要大量的計算資源與工程投入。參數高效微調（Parameter-Efficient Fine-Tuning, PEFT）技術提供了一個更實用的替代方案。

最流行的 PEFT 方法是 LoRA（Low-Rank Adaptation）。LoRA 的核心思想是：在微調過程中，凍結原始模型的權重，只訓練一小組額外的低秩矩陣來模擬權重更新。具體而言，對於一個權重矩陣 W，LoRA 將其更新表示為 Delta W = BA，其中 B 和 A 是兩個低秩矩陣。

```
h = Wx + Delta W x = Wx + BAx
```

假設 W 是一個 4096x4096 的矩陣（約 1670 萬個參數），使用 LoRA 時可以選擇 rank r=16，則 B 是 4096x16 的矩陣，A 是 16x4096 的矩陣，總共約 13 萬個參數——只有原始參數量的 0.8%。這使得 LoRA 微調可以在單個消費級 GPU 上完成，而無需數百 GB 的 GPU 記憶體。

LoRA 的優勢不僅在於記憶體效率。由於微調的參數數量很少，LoRA 模型檔案的體積很小（通常只有數十 MB），方便儲存與分發。LoRA 還可以實現任務切換：同時維護多個 LoRA 模組，在同一個基礎模型上快速切換不同的任務專屬行為。

QLoRA 是 LoRA 的進一步擴展，結合了 4-bit 量化技術，使得在 24GB 顯存的消費級 GPU 上也可以微調數十億參數規模的模型。這大大降低了 LLM 微調的硬體門檻。

### 知識蒸餾

知識蒸餾（Knowledge Distillation）是一種模型壓縮技術，核心思想是讓一個較小的學生模型（student model）去模仿一個較大的教師模型（teacher model）的行為。在 LLM 的語境中，知識蒸餾可以將大型模型（如 GPT-4、Claude）的能力遷移到更小、更高效的模型上。

蒸餾的基本流程如下。首先，使用教師模型對大量輸入產生輸出，這些輸出不僅包括最終的答案，還包括模型內部的機率分佈。然後，學生模型在這些資料上進行訓練，目標是讓自己的輸出盡可能接近教師模型的輸出。

蒸餾的關鍵在於訓練目標的設計。傳統的訓練目標是最大化正確答案的機率（硬目標），而蒸餾的訓練目標還包括了匹配教師模型的機率分佈（軟目標）。軟目標包含了教師模型對各種可能輸出的相對偏好——例如，在程式碼生成任務中，教師模型可能認為某個實作方案比另一個更好，這種偏好資訊體現在機率分佈中。學生模型透過學習這些偏好，可以獲得更豐富的知識。

硬目標損失與軟目標損失通常加權組合：

```
L_distill = alpha * L_hard + (1 - alpha) * L_soft
```

其中 L_hard 是標準的交叉熵損失（以真實標籤為目標），L_soft 是與教師模型機率分佈之間的 KL 散度（Kullback-Leibler divergence），alpha 控制兩者的權重。

在軟目標的計算中，溫度參數 T 扮演了重要角色。使用高溫可以讓機率分佈變得更加平滑，暴露教師模型在低機率區域的偏好：

```
P_i = exp(logit_i / T) / sum exp(logit_j / T)
```

更高的溫度會產生更平滑的分佈，讓學生模型可以學到教師模型對於各種候選方案的排序，而不僅僅是最可能的那一個。

知識蒸餾在 AI 軟體工程中有多種應用場景。模型壓縮是主要的應用方向——將數百億參數的 LLM 蒸餾為數十億參數的模型，使其可以在消費級硬體上運行，同時保留大部分能力。例如，在 IDE 程式碼補全場景中，一個經過蒸餾的小模型可以在毫秒級別內給出建議，而大型模型由於延遲較高，更適合用於需要深度理解的任務（如架構設計審查）。

特定的程式碼能力也可以作為蒸餾的目標。例如，將大型模型的程式碼審查能力蒸餾到較小的模型上，使其可以在 CI pipeline 中快速執行。或者將大型模型的除錯推理能力蒸餾到輕量級模型上，使其可以嵌入到開發者工具中提供即時的錯誤分析。

蒸餾資料的生成策略有多種形式。教師模型生成的輸出可以直接作為訓練資料，這種方式稱為白盒蒸餾。另一種方式是使用教師模型對大量真實世界的程式碼進行增強——生成多種實作方案、添加註解、生成測試案例等，然後讓學生模型在這些增強的資料上訓練，這種方式稱為資料增強蒸餾。

除了標準的輸出分佈匹配外，還有一些更進階的蒸餾方法。特徵蒸餾（Feature Distillation）讓學生模型不僅匹配教師模型的輸出，還匹配中間層的表示，這有助於學生模型學習更深層次的程式碼理解能力。對比蒸餾（Contrastive Distillation）利用正負樣本對比來讓學生模型學習更好的程式碼表示。關係蒸餾（Relational Distillation）則關注樣本之間的關係，讓學生模型學會教師模型對於程式碼片段之間相似度或差異的判斷。

在實際應用中，蒸餾的效果取決於多個因素。學生模型的架構設計需要與蒸餾任務匹配——對於程式碼生成任務，解碼器架構比編碼器架構更適合；教師模型的品質直接決定了蒸餾能力的上限，因此通常選擇當前最好的模型作為教師；蒸餾資料的覆蓋範圍需要足夠廣泛，涵蓋各種程式語言、框架與應用場景；訓練超參數（溫度、損失權重、學習率等）需要仔細調整以達到最佳平衡。

蒸餾的一個重要考量是模型能力的取捨。蒸餾後的模型通常在某些能力上接近教師模型，但在其他方面可能有所損失。例如，一個從 GPT-4 蒸餾而來的模型可能在程式碼生成上表現出色，但在處理複雜的邏輯推理或罕見的程式語言時可能不如教師模型。因此，在選擇蒸餾策略時，需要根據目標應用場景來決定需要保留哪些能力。

蒸餾與量化、剪枝等其他模型壓縮技術可以組合使用。典型的組合策略是先進行蒸餾（減少模型對參數量的需求），再進行量化（降低每個參數的精度），從而最大程度地壓縮模型體積。例如，一個 70B 的模型可以先蒸餾為 7B 的模型，再進行 4-bit 量化，最終體積從約 140GB 縮小到約 4GB，同時保留大部分能力。

近年來，蒸餾技術在開源模型的發展中扮演了重要角色。許多高效能的開源模型（如 Mistral、Phi 系列）都使用了某種形式的蒸餾技術。微軟的 Phi-3 模型系列就是一個典型案例——透過從 GPT-4 蒸餾高品質的訓練資料，Phi-3-mini（3.8B 參數）在許多基準測試上達到了比同級別模型更優的效果，甚至可以與一些 7B 甚至 13B 的模型競爭。

蒸餾也存在一些爭議與限制。從 API 服務蒸餾模型可能違反服務條款，這引發了關於模型智慧財產權的討論。蒸餾本質上是壓縮而非創造——蒸餾模型的能力上限由教師模型決定，無法超越教師模型。蒸餾過程中的偏見傳遞也是一個隱憂——如果教師模型存在偏見，這些偏見很可能會被蒸餾到學生模型中。

## 推理機制

LLM 的推理（inference）過程與訓練過程有顯著的不同。在推理階段，我們不再更新模型的參數，而是利用訓練好的模型來生成新的文字。

### 自回歸生成

當代 LLM 的基本生成方式是自回歸生成（autoregressive generation）。所謂自回歸，就是將生成過程分解為一系列的步驟，每一步根據已生成的 token 來預測下一個 token。

```
給定：The quick brown
預測下一個：fox

給定：The quick brown fox
預測下一個：jumps

給定：The quick brown fox jumps
預測下一個：over
```

這個過程會一直持續，直到生成結束 token（EOS token）或達到最大長度限制。

在每一步中，模型會輸出詞彙表中所有 token 的機率分佈。然後需要根據這個機率分佈來選擇下一個 token。不同的選擇策略會導致不同的生成結果。

### 解碼策略

**貪婪解碼（Greedy Decoding）**：在每一步選擇機率最高的 token。這種方法簡單快速，但容易產生重複與單調的輸出。貪婪解碼是確定性的——給定相同的輸入，總是產生相同的輸出。

**溫度採樣（Temperature Sampling）**：在從機率分佈中取樣之前，先對分佈應用溫度參數 T。溫度參數控制了輸出的隨機性。

```
P_i = exp(logit_i / T) / sum exp(logit_j / T)
```

當 T 趨近於 0 時，取樣行為接近貪婪解碼；當 T = 1 時，使用原始的機率分佈；當 T > 1 時，機率分佈變得更加平滑，低機率的 token 有更大的被選中機會。

在程式碼生成任務中，通常使用較低的溫度（0 到 0.2）來保證輸出的一致與可預測。在創意性任務（如產生註解或文件）中，可以使用稍高的溫度（0.7 到 0.9）來增加多樣性。

**Top-k 採樣**：只從機率最高的 k 個 token 中進行採樣，將低機率的 token 完全排除在外。這種方法可以避免生成非常不合理的 token。k 的典型值在 10 到 100 之間。

**Top-p 採樣（Nucleus Sampling）**：從累積機率達到 p 的最小 token 集合中進行採樣。與 Top-k 固定數量不同，Top-p 可以根據機率分佈的形狀動態調整候選 token 的數量。當分佈很集中時，候選集合小；當分佈很平均時，候選集合大。p 的典型值在 0.9 到 0.95 之間。

在實務中，常常將多種策略結合使用。例如，同時使用 Top-k（k=50）與 Top-p（p=0.95），並設置溫度為 0.7。這種組合可以在控制品質的同時保持一定的多樣性。

**Beam Search**：不同於上述的逐點解碼策略，beam search 維護一組（beam）部分序列，每一步對每個序列擴展多個候選，然後保留總體機率最高的 beam 個序列。Beam search 特別適合需要最大機率序列的任務（如機器翻譯），但在程式碼生成中較少使用，因為高機率序列不一定是最正確的序列。

### 上下文視窗

上下文視窗（context window）指的是模型在一次推理中可以處理的最大 token 數量。這個數量包括輸入（prompt）與輸出（generation）的總和。

早期的 LLM 上下文視窗較小。GPT-3 的上下文視窗為 2048 個 token，對於簡單的任務來說已經足夠，但對於需要處理大量上下文（如程式碼庫、長篇文件）的任務來說，顯得捉襟見肘。

2023 到 2026 年間，上下文視窗技術取得了重大突破。GPT-4 與 Claude 2 將上下文視窗擴展到 32K 與 100K token。Claude 3 進一步擴展到 200K token。GPT-4 Turbo 支援 128K token。Gemini 1.5 Pro 實做了高達 1M token 的上下文視窗，可以一次處理整個專案的程式碼。

更長上下文視窗的實現涉及多項技術創新。注意力機制的計算複雜度從原來的 O(n^2) 降低到 O(n log n) 或 O(n) 的近似方法，如 Flash Attention 與 sliding window attention。位置編碼方案的改進讓模型可以推廣到訓練時未見過的長度。高效的記憶體管理技術讓長序列的推理在硬體上變得可行。

上下文視窗的擴大對 AI 軟體工程具有重要意義。更大的上下文視窗意味著 AI 可以「看到」更多的程式碼，從而更好地理解專案結構、設計模式與編碼慣例。例如，一個擁有 1M token 上下文視窗的模型可以一次讀取整個中型專案的所有原始碼，並基於對整個專案的理解來生成與修改程式碼。

### KV Cache

在自回歸生成過程中，每一步都需要計算注意力分數。注意到在生成第 t+1 個 token 時，前 t 個 token 的鍵（K）與值（V）向量在之前的步驟中已經計算過了。如果不做任何最佳化，每步都需要重新計算所有前序 token 的 K 與 V，這會導致極大的計算浪費。

KV Cache 是最常用的最佳化技術。它的做法是將每一步計算得到的 K 與 V 向量儲存在記憶體中（快取），後續步驟直接從快取中讀取，而不需要重新計算。這將自回歸生成每一步的計算複雜度從 O(t^2) 降低到 O(t)。

KV Cache 的代價是記憶體消耗。當上下文長度為 n、模型層數為 L、每層隱藏維度為 d、注意力頭數為 h、精度為 fp16 時，KV Cache 的大小為 2 * n * L * d * 2 bytes。對於一個 70B 參數的模型（L=80, d=8192），上下文長度為 128K 時，KV Cache 需要約 320 GB 的記憶體——這遠遠超過了單個 GPU 的記憶體容量。

因此，如何在有限的記憶體中高效管理 KV Cache 是一個重要的工程問題。常見的策略包括：使用更低的精度來儲存 KV Cache（如 INT8 或 FP8 量化）、使用記憶體共享技術（如 PagedAttention）、以及在多個 GPU 之間分片（shard）KV Cache。

## 程式碼專用模型

通用 LLM（如 GPT-4、Claude）在程式碼任務上表現已經相當出色，但專門針對程式碼進行最佳化的模型往往在程式碼生成相關任務上表現更佳。這些模型在訓練資料、訓練方法、評估基準等方面都有獨特之處。

### Codex

Codex 是 OpenAI 於 2021 年發表的第一個大規模程式碼專用 LLM，也是 GitHub Copilot 的基礎模型。

Codex 基於 GPT-3 架構，在包含大量 GitHub 公開程式碼的資料集上進行了微調。訓練資料集包含 179GB 的 Python 程式碼（約 54M 個 GitHub repository）。Codex 展現了從自然語言描述生成 Python 程式碼的強大能力，在 HumanEval 基準測試上（一組程式設計問題，要求模型生成通過測試的函式），Codex 的通過率達到了 28.8% 到 72.3%（取決於模型規模與使用的最佳化技術）。

Codex 的成功展示了兩個重要的洞察：一是使用大量高品質的程式碼資料進行微調可以顯著提升程式碼生成能力；二是程式碼生成任務可以透過簡單的功能正確性評估（functional correctness）來客觀衡量。

### StarCoder

StarCoder 由 BigCode 專案（Hugging Face 與 ServiceNow 的合作專案）開發，是一個完全開放的程式碼專用模型系列。與 Codex 不同，StarCoder 的模型權重、訓練資料、訓練流程都是完全公開的。

StarCoder 的基礎模型訓練資料來自 The Stack，這是一個包含超過 6TB 原始碼資料的大型資料集，涵蓋數百種程式語言。StarCoder 在預訓練過程中使用 FIM 任務，此外還進行了 Python-only 的微調（StarCoderBase -> StarCoder）。

StarCoder 的獨特之處在於它的開放性。研究人員可以完整地審視、分析與複製模型的訓練過程，這對學術研究與技術進步具有重要價值。StarCoder 也推動了社群對程式碼專用模型的共同開發與改進。

### Code Llama

Code Llama 由 Meta AI 於 2023 年發表，基於 Llama 2 模型，是一個專注於程式碼生成的模型系列。Code Llama 提供了三種變體：Code Llama（基礎模型）、Code Llama Python（專注於 Python 的版本）、以及 Code Llama Instruct（針對指令微調的版本）。

Code Llama 在訓練資料上使用了額外的程式碼資料，並應用了 FIM 任務。模型規模從 7B 到 34B 參數不等，滿足了不同場景的需求。在 HumanEval 基準測試上，Code Llama 34B 的通過率達到了 48.8%（貪婪解碼），在 MBPP（Mostly Basic Python Programming）上達到了 62.5%。

Code Llama 的開源釋出對產業產生了重要影響。它讓研究人員與開發者可以在自己的基礎上進行微調與客製化，而不需要從頭開始訓練。許多後續的開源模型都基於 Code Llama 進行了改進。

### DeepSeek Coder

DeepSeek Coder 由 DeepSeek（深度求索）公司開發，是一個完全開放的程式碼專用模型。DeepSeek Coder V2 在 2024 年發表，展示了開放模型可以達到與頂尖閉源模型（如 GPT-4 Turbo）相當的程式碼生成能力。

DeepSeek Coder V2 基於 DeepSeek-V2 架構，採用了 Mixture of Experts（MoE）設計。MoE 技術將模型劃分為多個專家（expert）子網路，在推理時只啟用與當前輸入相關的專家。這使得模型可以在不顯著增加推理成本的前提下擁有更多的總參數。

DeepSeek Coder V2 在 HumanEval 上達到了 90.2% 的通過率，在 MBPP 上達到了 76.2%，在多語言程式碼生成基準 MultiPL-E 上也表現出色。這些結果表明，開放模型的程式碼生成能力正在快速追趕閉源模型。

DeepSeek Coder 在訓練資料上的特點是：大量的多語言程式碼資料、包含自然語言與程式碼的配對資料、以及針對特定程式語言的平衡取樣策略。此外，DeepSeek Coder 在預訓練階段使用了 4K 到 16K 的長序列，支援更長的上下文。

### FIM 在程式碼專用模型中的應用

如前所述，FIM（Fill in the Middle）是程式碼專用模型中廣泛使用的預訓練任務。FIM 對於程式碼補全的實際應用場景非常重要——開發者通常不在檔案末尾寫程式碼，而是在檔案的中間位置插入新的程式碼或修改現有的程式碼。

FIM 的實作方式有多種變體。最常見的方法是，在預訓練資料中隨機選取一段程式碼作為「中間」部分，然後將這段程式碼移動到序列的最後，同時在開頭與中間之間插入一個 sentinel token（如 `<FILL_HERE>`），在中間與結尾之間插入另一個 sentinel token（如 `<FILL_END>`）。模型需要從前文與後文中推斷出中間的內容。

```
原始序列：[A][B][C]
FIM 改寫後：[A][C]<FILL_HERE>[B]
```

經過 FIM 訓練的模型在 IDE 程式碼補全場景中表現顯著優於僅使用從左到右語言建模訓練的模型。

### 評估基準

程式碼專用模型的評估通常使用以下幾個基準測試。

**HumanEval**：包含 164 個手寫的 Python 程式設計問題。每個問題包含函式簽章、文件字串（docstring）與多個測試案例。模型需要根據問題描述生成完整的函式實作。評估指標是 pass@k——在 k 次生成中至少有一次通過所有測試案例的機率。

**MBPP（Mostly Basic Python Programming）**：包含約 1000 個 Python 程式設計問題。與 HumanEval 類似，但問題難度通常略低。

**MultiPL-E**：HumanEval 的多語言擴展版本，將 HumanEval 的問題翻譯為 18 種程式語言（包括 JavaScript、TypeScript、Java、Go、Rust、C++ 等）。MultiPL-E 可以用來評估模型在多語言環境下的程式碼生成能力。

**SWE-bench**：一個更具挑戰性的評估基準，測試模型在真實世界軟體專案中的 Bug 修復能力。給定一個 GitHub issue 與專案的程式碼庫，模型需要生成修補程式（patch）來解決問題。SWE-bench 更接近真實的開發場景，因此被認為是更貼近實務的評估方式。

**BigCodeBench**：針對程式碼專用模型的綜合性評估框架，包含多種任務類型（程式碼生成、程式碼補全、程式碼解釋、程式碼翻譯等）與多種評估指標（功能性、正確性、效率、安全性等）。

## 嵌入與向量表示

嵌入（Embedding）是將離散的符號（如單詞、token、程式碼片段）映射到連續的向量空間中的技術。嵌入向量捕捉了符號的語意資訊——語意相似的符號在向量空間中彼此靠近。

### Token Embedding

在 LLM 中，嵌入的第一層是 token embedding。給定一個輸入 token 序列，token embedding 層將每個 token 對應到一個固定維度的向量。這些向量是透過查詢一個嵌入表（embedding table）得到的，嵌入表的大小為詞彙表大小乘以嵌入維度。

例如，在 GPT-3 中，詞彙表大小約為 50,000，嵌入維度為 12,288，因此 token embedding 層的參數量約為 614M（6.14 億個參數）。

Token embedding 的初始值是隨機的，在預訓練過程中透過反向傳播來學習。訓練完成後，語意相似的 token 在嵌入空間中會彼此靠近。

### 程式碼的嵌入表示

程式碼的嵌入表示與自然語言的嵌入表示有些不同。程式碼同時具有靜態結構（語法樹）與動態行為（執行語意），要讓嵌入表示捕捉這些資訊需要特殊的設計。

CodeBERT 是程式碼嵌入的早期重要工作。CodeBERT 使用 BERT 架構，在自然語言-程式碼配對資料上進行預訓練。CodeBERT 的嵌入同時考慮了自然語言描述與程式碼本身，因此在自然語言檢索程式碼的任務上表現出色。

GraphCodeBERT 在 CodeBERT 的基礎上加入了程式碼的資料流程圖（data flow graph）資訊。資料流程圖捕捉了變數之間的依賴關係，這些關係不一定在程式碼的序列結構中直接體現。透過引入資料流資訊，GraphCodeBERT 能夠更好地理解程式碼的語意。

### 向量檢索

嵌入向量的一個重要應用是向量檢索（vector retrieval）。給定一個查詢（query），將其編碼為向量，然後在向量資料庫中尋找與該查詢向量最相似的向量。

向量檢索在 AI 軟體工程中有多種應用。語意程式碼搜尋——給定自然語言查詢（如「尋找處理使用者認證的函式」），檢索出相關的程式碼片段。文件檢索——在 RAG 系統中，從文件庫中檢索與當前任務相關的文件。相似程式碼檢測——給定一段程式碼，尋找專案中與其語意相似的程式碼。重複程式碼（code clone）檢測——透過向量相似度來識別專案中的重複程式碼。

向量檢索的相似度度量通常使用餘弦相似度（cosine similarity）或內積（dot product）。為了提高大規模檢索的效率，可以使用近似最近鄰居（Approximate Nearest Neighbor, ANN）演算法，如 HNSW（Hierarchical Navigable Small World）或 IVF（Inverted File Index）。

### RAG 技術

檢索增強生成（Retrieval-Augmented Generation, RAG）是一種將檢索與生成結合的技術。在 AI 軟體工程的場景中，RAG 的工作原理如下：

當開發者向 AI 提出問題時，系統首先從知識庫（可以是文件、API 規格、既有程式碼庫等）中檢索與問題相關的片段，然後將這些片段連同問題一起輸入到 LLM 中，讓 LLM 根據檢索到的資訊來生成答案。

RAG 的優勢是顯而易見的。透過檢索，AI 可以獲取最新的、特定於專案的資訊，而不僅僅依賴於訓練資料中的靜態知識。檢索可以大幅擴展 AI 的「有效知識庫」，而無需增加模型的參數量。RAG 讓 AI 的輸出可以被追溯到來源，增加了結果的可信度與可驗證性。

在實際應用中，RAG 已經成為 AI 軟體工程工具的重要組成部分。例如，一些對話式 AI 工具可以透過 RAG 來檢索專案的文件、API 規格或既有程式碼，從而給出更精確、更符合專案上下文的回答。
